# K8S 자원 관리 운영 매뉴얼 (`/k8s-allocation`)

노드/네임스페이스/워크로드별 request 대비 실사용(slack)을 보여주는 용량 계획 화면과, 그 위에서
동작하는 **자원 효율화 자동화**(효율화 탭)를 실제로 운영하기 위한 문서다.

- 화면 구조/파일 매핑: `docs/SCREENS.md` 의 「K8S 자원 관리」 섹션
- 효율화의 내부 구조(수집→추천 알고리즘→적용/롤백→안전장치, Celery 흐름, DB 스키마): 개발자용
  설계 문서 `docs/02-design/k8s-efficiency-automation.md` — 이 매뉴얼은 "화면에서 무엇을 어떻게
  누르는가"에 집중하고, 내부 구조는 필요한 만큼만 쉬운 말로 풀어 쓴다.
- 코드 위치: `backend/app/routers/{k8s_allocation,k8s_efficiency}.py` ·
  `backend/app/services/k8s_efficiency/` · `frontend/src/components/k8s-allocation/`

## 1. 한 장 요약

| 하고 싶은 것 | 어디서 |
|---|---|
| 노드/NS 별 request 대비 실사용(낭비/위험) 보기 | **노드** / **네임스페이스** / **NS 랭킹** 탭 |
| 지금 몇 개나 더 스케줄할 수 있는지 계산 | 클러스터 요약 카드의 `PodScheduleCalc`(CPU/MEM 입력) |
| 점유는 큰데 실제로 안 쓰는 워크로드 찾기 | **효율화** 탭 → 추천 테이블 |
| 추천을 실제로 적용(request 축소) | 추천 테이블 체크 → **선택 적용** → 드라이런 먼저 |
| 잘못 적용한 걸 되돌리기 | 실행 이력에서 그 run 을 펼쳐 **롤백** |
| 특정 NS 만 사람 개입 없이 자동으로 줄어들게 하기 | **정책 설정** → 네임스페이스 정책 → **자동 right-size(opt-in)** |
| NS 가 자원 부족/미사용일 때 Quota 를 자동으로 늘리고/회수 | **정책 설정** → 네임스페이스 정책 → **ResourceQuota 탄력(opt-in)** + min/max |
| StarRocks CN 처럼 오퍼레이터(CR)가 관리하는 워크로드 늘리기 | **정책 설정** → 네임스페이스 정책 → **오퍼레이터 CR 어댑터** 등록 |
| 수집이 왜 오래 걸리는지 / 왜 안 됐는지 확인 | 실행 이력에서 **건너뜀(skipped)** 항목 빈도 확인 → §7 |
| 특정 클러스터 수집 주기 조정 | **정책 설정** → 수집 스케줄 → 클러스터 cron 오버라이드 |

조회는 로그인한 사용자면 누구나 가능하다. **지금 수집 / 추천 재생성 / 적용 / 무시 / 롤백 /
NS 정책 저장**은 operator 이상, **전역 기본값 / 수집 스케줄 저장**은 admin 이 필요하다.

## 2. 화면 구성

좌측 `ClusterSidebar` 로 클러스터 하나를 고르면 4개 탭이 뜬다.

| 탭 | 보여주는 것 |
|---|---|
| **노드** | 노드별 allocatable vs request vs 실사용 게이지. 카드/테이블 토글, 정렬·검색·CSV. 48노드를 넘으면 자동으로 가상 스크롤로 전환된다(그 이하에서는 평범한 그리드/테이블) — 300노드급 클러스터도 화면이 느려지지 않는다. |
| **네임스페이스** | NS → 워크로드 → 파드 드릴다운. 페이징. |
| **NS 랭킹** | request 대비 실사용 막대 랭킹 — 어느 NS 가 가장 낭비가 큰지 한눈에. |
| **효율화** | 이 문서의 주제. §3~§7. |

상단 요약 카드(클러스터 요약, POD 용량/상태)는 화면 어느 탭에 있든 항상 같은 시점의 값이다 —
같은 스냅샷에서 함께 계산되기 때문에 탭을 옮겨도 숫자가 서로 어긋나지 않는다.

집계 중에는 화면 상단 고정 슬롯에 진행률 바가 뜬다. 502 나 화면이 계속 바뀌는 문제는 과거
이슈였고 지금은 스냅샷을 클러스터당 1개만 만들도록 고쳐졌다 — 진행률은 어느 탭에서 봐도
똑같이 올라간다.

## 3. 효율화 탭이 하는 일 (동작 방식, 쉬운 말로)

효율화는 큰 그림에서 4단계로 돈다.

```
① 수집 (주기적으로, 또는 "지금 수집" 버튼)
     NS/워크로드 단위로 request·실사용·Quota 사용량을 기록에 남긴다.
     ▼
② 추천 (수집 직후 자동으로, 또는 "추천 재생성" 버튼)
     최근 사용량이 request 보다 훨씬 낮은 컨테이너에 "이만큼 줄이세요"를 추천한다.
     ▼
③ 적용 (사람이 확인 → 버튼) 또는 자동 적용 (NS 별로 opt-in 한 경우에만)
     드라이런으로 먼저 검증하고, 실제로 적용하면 실행 로그와 함께 남는다.
     ▼
④ 필요하면 롤백
     적용 직전 값을 기억해뒀다가 그대로 되돌린다.
```

**추천 규칙**은 "최근 관측된 사용량의 상위 백분위(기본 p95)에 여유율(기본 30%)을 더한 값"을
목표로 잡고, 지금 설정된 request 가 그 목표보다 **뚜렷하게**(임계 비율 이상, 그리고 절감량이
최소 기준 이상) 클 때만 추천한다. 살짝 여유 있는 정도로는 추천하지 않는다 — 이 임계값들은
전부 §4.3 의 **전역 기본값** 탭에서 조정할 수 있다.

**추천이 나가지 않는 경우**(정상 동작):
- 수집이 아직 충분히 쌓이지 않음(기본 24시간·12샘플 이상 필요) — "데이터 부족"으로 표시.
- 시스템 네임스페이스(kube-system 등)이거나, NS/워크로드에 opt-out annotation 이 붙어 있음.
- DaemonSet(기본 제외, 옵션으로 포함 가능) 이거나 request 자체가 없는 컨테이너.

**적용이 막히는 경우** — **오퍼레이터(CR) 관리 워크로드**. 예를 들어 StarRocks CN 의 StatefulSet
은 `StarRocksCluster` 커스텀 리소스가 관리하고 있어서, PEP 가 StatefulSet 을 직접 고쳐도
오퍼레이터가 곧바로 원래 값으로 되돌려버린다. 이런 워크로드는 추천 테이블에 **"오퍼레이터
관리 — CR로 조정"** 배지가 붙고 체크박스가 비활성화된다 — 서버도 적용 요청을 422 로 거부한다.
이 경우는 request 를 직접 건드리지 말고 §4.3 의 **오퍼레이터 CR 어댑터**로 CR 필드(예: replicas)
를 조정한다.

> 자동 적용은 기본적으로 전부 **꺼져 있다**(전역 마스터 스위치 off). 수집·추천은 배포 즉시
> 계속 돌지만, 실제로 request 를 바꾸는 건 사람이 버튼을 누르거나 NS 별로 명시적으로 켠
> 경우뿐이다. 안전장치는 §4.4 에서 순서대로 켜는 법을 다룬다.

## 4. 사용법 — 버튼별

### 4.1 지금 수집 / 추천 재생성

- **지금 수집**(▶ 아이콘) — 이 클러스터의 노드/파드를 한 번 전수 순회해 NS·워크로드 샘플을
  새로 쌓고, 이어서 추천도 다시 계산하고, opt-in 된 NS 가 있으면 자동화까지 평가한다. 대형
  클러스터는 시간이 걸릴 수 있다(§7 참고).
- **추천 재생성**(순환 아이콘) — 새로 수집하지 않고 **지금까지 쌓인 샘플만으로** 추천 규칙을
  다시 계산한다. 정책 설정(백분위·여유율 등)을 바꾼 직후 결과를 바로 보고 싶을 때 쓴다.

두 버튼 모두 누르는 즉시 실행 이력에 run 이 생기고, 기본 설정이면 **실행 로그**가 바로 펼쳐진다
(§6).

### 4.2 추천 적용하기

1. 추천 테이블에서 원하는 행(들)을 체크한다 — 헤더의 "전체 선택"은 적용 가능한(오퍼레이터
   관리가 아닌) 행만 고른다.
2. 우측 하단 **선택 적용 (N)** 버튼을 누르면 적용 확인 창이 뜬다 — 컨테이너별 현재값 →
   목표값(before/after)이 한눈에 보인다.
3. 체크박스 두 개를 확인한다.
   - **드라이런(검증만, 변경 없음)** — 기본으로 켜져 있다. apiserver 에 `dry-run=All` 로 보내
     유효성만 확인하고 실제로는 아무것도 바뀌지 않는다. **처음엔 항상 이걸로 먼저 확인한다.**
   - **실행 후 실시간 로그 보기** — 켜두면 실행 즉시 로그 패널이 펼쳐진다(선택은 다음에도
     기억된다).
4. **드라이런 실행**(또는 **적용 실행**)을 누르면 대상별로 순서대로 처리되고 로그에 단계가
   쌓인다. 하나가 실패해도 나머지는 계속 진행하고 결과는 **부분 성공**으로 남는다.
5. 실제 적용은 컨테이너의 requests(그리고 Guaranteed 유지 옵션이 켜져 있으면 limits 도)를
   바꾸는 롤링 업데이트를 일으킨다 — 드라이런이 아니면 파드가 재시작될 수 있다는 뜻이다.

개별 추천이 마음에 안 들면 체크하지 않고 행의 **X**(무시) 버튼으로 그 추천만 뺄 수 있다 —
다음 추천 재생성 때 조건이 다시 맞으면 재등장할 수 있다.

**롤백**은 실행 이력에서 그 run 을 펼치면 보인다(§6) — 드라이런이 아니고, 상태가 **성공** 또는
**부분 성공**인 적용 run 에서만 나타난다. 누르면 적용 직전에 기록해둔 값(before) 그대로
되돌리는 새 run 이 생긴다.

### 4.3 NS 정책 설정하기 — **정책 설정** 다이얼로그

툴바의 **정책 설정** 버튼을 누르면 탭 3개가 뜬다.

**전역 기본값**(admin) — 클러스터 전체에 적용되는 기본 규칙.
- **자동 적용** 마스터 스위치(기본 꺼짐) + 허용 시간대(cron, 비우면 항상 허용).
- 추천 규칙: 백분위(p) · 관측 창(일) · 여유율(headroom %) · CPU/MEM 하한 · 임계 비율 ·
  최소 절감량(CPU/MEM, 파드당) · DB 샘플일 때 최소 샘플 수/관측 기간.
- 자동 적용 안전장치: 쿨다운(분) · 1회 최대 감소폭(%) · run 당 최대 대상 수.
- 제외 규칙: opt-out annotation 키 · 시스템 네임스페이스 목록 · DaemonSet 포함 여부 ·
  Guaranteed(req=lim) 유지 여부.
- ResourceQuota 탄력 기본값: 확장/회수 임계(used/hard), 회수 지속 시간, 회수 후 배율, 확장
  폭(%), 쿨다운.

**네임스페이스 정책**(operator 이상) — NS 를 골라 그 NS 만의 설정을 켠다.
- **자동 right-size(opt-in)** — 켜야 그 NS 의 추천이 자동 적용 대상이 된다(마스터 스위치도
  같이 켜져 있어야 실제로 동작한다).
- **ResourceQuota 탄력(opt-in)** — 켜고 CPU/MEM 최소·최대를 지정하면, 사용률이 높을 때
  자동으로 Quota 를 늘리고 오래 낮으면 회수한다. **라이브 Quota 불러오기** 버튼으로 지금
  클러스터에 실제 걸린 Quota 값을 그대로 채울 수 있다 — min/max 는 반드시 지정하고 시작한다.
- 전역 값을 이 NS 만 다르게 쓰고 싶으면 headroom/쿨다운/최대 감소폭/Quota 임계를 오버라이드
  칸에 넣는다(비우면 전역 값을 그대로 따른다).
- **오퍼레이터 CR 어댑터** — "행 추가"로 group/version/plural/name/jsonpath/min/max 를 등록하면
  (예: StarRocks CN → `group=starrocks.com, plural=starrocksclusters, jsonpath=spec.starRocksCnSpec.replicas`)
  request 대신 이 CR 필드를 조정 대상으로 삼는다. **자동** 토글을 켜두면 NS 사용률이 높을 때
  +1, 낮을 때 −1 로 자동 조정된다. 수동으로 값을 바꾸고 싶으면 이 화면이 아니라 효율화 탭의
  해당 API(`custom-targets/scale`)를 쓰는 별도 조작이 필요하다 — 자동 조정이 기본이다.

**수집 스케줄**(admin) — 전체 켬/끔, 기본 cron, 그리고 **클러스터별 cron 오버라이드**. 오버라이드
칸을 비우면 기본 cron 을 따른다. 다음 실행/마지막 수집 시각이 여기 함께 보인다.

### 4.4 자동 적용을 실제로 켜는 순서 (권장)

1. 드라이런으로 몇 개 추천을 검증한다(§4.2) — before/after 값이 기대한 대로인지 확인.
2. 소수 워크로드에 **실제로** 적용해보고, 파드가 정상적으로 재시작되는지 확인한다.
3. 그 run 을 **롤백**해서 원래 값으로 정확히 돌아오는지 확인한다.
4. 자동으로 맡겨도 되는 네임스페이스만 **네임스페이스 정책**에서 opt-in 한다(처음엔 소수만).
5. 전역 **자동 적용** 마스터 스위치를 켠다.
6. 실행 이력에서 `trigger = auto` 인 run 들을 당분간 지켜본다.

ResourceQuota 탄력은 별개로, **min/max 를 반드시 지정**한 뒤에 opt-in 한다 — 안 그러면 임계값
계산 자체가 스킵된다.

## 5. 추이 차트 읽는 법

- **네임스페이스 자원 추이**(NsTrendChart) — NS 를 골라 request/실사용/Quota 한도 시계열을
  본다(24h/7d/30d, CPU/MEM 토글은 위쪽 공용 컨트롤). "Quota 한도 표시" 를 켜면 그 NS 의 Quota
  hard/used 선이 같이 그려진다 — request 선이 Quota 한도에 계속 붙어 있으면 조만간 Quota 확장이
  필요하다는 신호다.
- **저효율 네임스페이스 추이**(LowEfficiencyRankingChart) — 사용효율(실사용/request)이 낮은 NS
  상위 8개를 시계열로 겹쳐 보여주고, 옆 목록에 현재 효율·평균 낭비량·추세 화살표(↑개선/↓악화/
  →보합)를 같이 준다. 목록에서 NS 를 클릭하면 왼쪽 추이 차트가 그 NS 로 바뀐다 — 랭킹에서 눈에
  띄는 NS 를 클릭해 바로 상세 추이를 보는 흐름으로 쓰면 된다.

## 6. 실행 로그 / 이력 확인하기

이 화면의 모든 실행 버튼(지금 수집·추천 재생성·적용·롤백·Quota 조정·CR 스케일)은 예외 없이
**실행 이력**에 한 줄로 남고, 실시간 로그를 볼 수 있다 — PEP 의 "실행 버튼은 항상 상세 로그 +
로그 보기 옵션" 규칙이 여기도 그대로 적용된다.

- 버튼을 누르면 즉시 run 이 생성되고, "로그 보기" 설정이 켜져 있으면(체크박스/토글, 마지막
  선택이 기억된다) **단계 타임라인 + 로그 뷰어**가 바로 펼쳐진다. 로그는 1.5초 간격으로
  자동 갱신되며, run 이 끝나면 멈춘다.
- 툴바 아래 **실행 이력** 패널에서 과거 run 들을 볼 수 있다. 행을 클릭하면 그 run 의 로그가
  펼쳐진다(현재 진행 중이 아니어도 지난 로그 그대로 남아 있다).
- 상태 배지는 6가지다.

  | 배지 | 뜻 |
  |---|---|
  | 대기 | 큐에 들어갔고 아직 시작 전 |
  | 실행 중 | 지금 처리 중 — 로그가 실시간으로 늘어난다 |
  | 성공 | 전체 대상이 문제없이 끝남 |
  | 부분 성공 | 일부 대상만 실패 — 로그에서 어느 대상이 실패했는지 확인 |
  | 실패 | 수집/추천/자동화 단계 자체가 실패 |
  | **건너뜀** | 이 클러스터의 직전 실행이 아직 진행 중이라 이번 실행은 무거운 작업 없이 바로 건너뛴 것(§7) |

## 7. 트러블슈팅

| 증상 | 확인할 것 |
|---|---|
| 추천이 하나도 안 뜬다 | 배포 직후이거나 수집이 얼마 안 됐으면 정상이다(기본 24시간·12샘플 필요 — "데이터 부족"). 시스템 NS·opt-out annotation·DaemonSet 은 기본 제외. |
| 적용 체크박스가 회색이고 "오퍼레이터 관리" 배지가 붙어 있다 | StarRocks CN 처럼 CR 이 관리하는 워크로드다. request 를 직접 적용할 수 없다 — 정책 설정 → 네임스페이스 정책 → 오퍼레이터 CR 어댑터로 조정한다(§4.3). |
| 실행 이력에 **건너뜀(skipped)** 이 자주 보인다 / 최근 수집이 오래 안 됐다 | 대형 클러스터(수백 노드급)는 전수 수집 1회가 기본 수집 주기(10분)보다 오래 걸릴 수 있다. 겹쳐 쌓이지 않도록 클러스터당 한 번에 하나만 돌게 막아뒀는데, 그 결과가 "건너뜀"으로 남는 것이다 — 정책 설정 → 수집 스케줄에서 이 클러스터의 cron 오버라이드를 늘린다. 수집 자체는 계속 되고 있으니 데이터가 아예 끊기는 건 아니다. |
| Celery 워커 부하가 계속 높다 | 위와 같은 원인일 가능성이 크다 — 실행 이력에서 건너뜀 비율을 먼저 본다. |
| 자동 적용이 켜져 있는데 아무 것도 안 된다 | 순서대로 확인: ① 전역 마스터 스위치 ON 인지 ② 그 NS 가 opt-in 됐는지 ③ 쿨다운 기간(기본 24시간) 안인지 ④ 허용 시간대 cron 을 벗어난 시간인지. |
| ResourceQuota 가 자동으로 안 늘어난다/안 줄어든다 | 그 NS 의 min/max 가 지정돼 있는지부터 확인 — 안 정해져 있으면 조정 자체가 스킵된다. 회수는 sustain 시간(기본 24시간) 내내 낮아야 실행된다. |
| 롤백 버튼이 안 보인다 | 드라이런 run 이거나, 수집/추천 재생성 같은 적용이 아닌 run 이거나, 상태가 성공/부분성공이 아니면(실패·건너뜀) 롤백 대상이 아니다. |
| 노드 탭이 버벅인다(수백 노드 클러스터) | 48노드를 넘으면 자동으로 가상 스크롤로 전환된다 — 그래도 느리면 자동갱신 주기를 늘리거나 끈다. |
